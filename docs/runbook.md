# Runbook релиза и инцидентов (REL-04)

Действующая инфраструктура: один VPS, `docker compose` (тот же
`docker-compose.yml`, что и для локального production-like окружения,
OPS-02). Никакого отдельного CD-пайплайна нет — CI (`ci.yml`) только
собирает, линтит и гоняет тесты на каждый PR/push в `main`, деплой ручной.

Ответственный за релизы и инциденты — один человек (автор проекта). Ничего
из ниже описанного не подразумевает дежурство команды или эскалацию —
только чек-лист для себя самого в момент, когда что-то ломается.

## Deploy

1. Убедиться, что `main` зелёный в CI (build/lint/unit/contract/integration).
2. На VPS:
   ```bash
   cd /path/to/kupidon-api
   git fetch origin
   git checkout <commit-or-tag>   # обычно origin/main
   docker compose up -d --build
   ```
   `depends_on: condition: service_healthy` не даст контейнеру `api`
   запуститься раньше, чем MongoDB, Redis и MinIO пройдут собственный
   healthcheck — это не гарантия успешного деплоя, только гарантия
   правильного порядка старта.
3. Проверить приложение, а не только контейнеры:
   ```bash
   curl -sf http://127.0.0.1:8000/health/ready
   ```
   Ожидается `{"status":"ok","mongo":"up","redis":"up"}`. Если процесс
   поднялся, но зависимость не готова, ответ — `503` с указанием, что
   именно не готово (`mongo`/`redis`).
4. Секреты (`config.yaml` на VPS) не трогаются деплоем — они не в Git и не
   в образе (см. «Управление секретами» в `README.md`), редактируются
   вручную на сервере до или после `docker compose up`.
5. Если менялась схема relationship-индексов — это отдельный, не автоматический
   шаг перед деплоем: `npm run migrate:relationships:apply` (см. README,
   «Безопасное создание relationship-индексов»). Обычный деплой его не
   запускает.

Даунтайм при деплое: `docker compose up -d --build` пересоздаёт контейнер
`api`, старый останавливается перед стартом нового — на один VPS без
второго инстанса это несколько секунд простоя на каждый деплой (graceful
shutdown даёт текущим соединениям `SHUTDOWN_GRACE_PERIOD_MS` = 5с на
завершение, но новых подключений в этот момент уже никто не принимает).
Это принятый для текущего масштаба компромисс, не баг.

## Rollback

Нет отдельного registry с тегированными образами — образ собирается на
самом VPS из чекаутнутого кода. Rollback = откат кода, затем пересборка:

```bash
git log --oneline -10          # найти последний известно-хороший коммит
git checkout <known-good-sha>
docker compose up -d --build
curl -sf http://127.0.0.1:8000/health/ready
```

Если проблема — в свежей миграции индексов (`migrate:relationships:apply`),
откат кода её не отменяет: индексы и слитые дубли (диалоги/сообщения)
остаются. Обратной команды нет («Удалённые дубли эта команда не
восстанавливает» — README) — для полного отката состояния БД к моменту
до миграции нужен предварительный бэкап (см. ниже) и восстановление.

Если проблема пережила rollback кода (например, повреждённые данные) —
следующий шаг это восстановление MongoDB из бэкапа, не повторный rollback.

## Ротация секретов

Подробная процедура — README, раздел «Управление секретами». Сжато для
инцидента:

- **JWT (`jwt.secret`, `jwt.secret_refresh`) скомпрометирован**: сменить
  оба значения в `config.yaml` на VPS, `docker compose up -d --build`.
  Разом инвалидирует все текущие access- и refresh-токены у всех
  пользователей — это ожидаемый эффект, а не побочный ущерб: пользователи
  просто заново проходят OTP. Ротации без даунтайма для этого секрета нет
  осознанно (см. README).
- **Ключ шифрования сообщений скомпрометирован**: добавить новую запись в
  `encryption.keys` с новым `version`, поднять `encryption.currentVersion`,
  передеплой. Старые сообщения остаются читаемыми под старым ключом (это
  ожидаемо — версия ключа хранится на сообщении), но если ключ и
  зашифрованные им сообщения уже были у атакующего одновременно, эти
  конкретные сообщения задним числом не защитить — полная защита
  требует перешифровки истории, сейчас не автоматизирована.
- **Секрет хранилища (MinIO/S3) скомпрометирован**: сменить
  `storage.secretAccessKey` в `config.yaml` и в самом хранилище
  (для MinIO — `MINIO_ROOT_PASSWORD` в `docker-compose.yml` + пересоздание
  volume или смена пароля через MinIO admin, для внешнего S3 — в консоли
  провайдера), затем передеплой.

## Восстановление MongoDB из бэкапа

Полная процедура — README, раздел «Backup и восстановление MongoDB».
В момент инцидента:

```bash
docker compose exec mongo-backup /scripts/restore.sh /backups/kupidon-<timestamp>.archive.gz.enc
```

Это `mongorestore --drop` — разрушительная операция для целевой базы;
подтвердить, что откатываемся действительно на актуальный бэкап и что
текущее состояние БД потеряно осознанно, а не просто временно недоступно
(если недоступна не сама БД, а её процесс/сеть — см. ниже, «MongoDB
недоступна», это другой сценарий и восстановление тут не нужно).

RPO при дефолтных настройках — до 24 часов (`BACKUP_INTERVAL_SECONDS`);
если инцидент произошёл незадолго после последнего дампа, потери за
промежуток между дампами не восстановить этим путём.

## MongoDB недоступна

`GET /health/ready` немедленно отражает это (`mongo: "down"`). На одном
VPS без внешнего балансировщика, который сам умеет читать `/health/ready`,
это НЕ останавливает автоматически маршрутизацию трафика — nginx/ingress
перед API продолжит присылать запросы, они будут падать с `5xx` по мере
обращения к базе. Контейнер `api` также не перезапускается сам по
unhealthy-статусу — здесь нет supervisor'а, который бы на это реагировал
(`restart:` политика в `docker-compose.yml` не задана).

Действия:
1. `docker compose ps` / `docker compose logs mongodb` — жив ли контейнер,
   не упал ли по OOM, не забита ли volume-партиция диском.
2. Если контейнер жив, но не healthy — `docker compose restart mongodb`,
   дождаться healthcheck (`mongosh --eval "db.runCommand('ping').ok"`).
3. Если контейнер не поднимается вообще — проверить свободное место на
   диске VPS (`df -h`) и `docker compose logs mongodb` на recovery-ошибки
   WiredTiger. Если данные повреждены — восстановление из бэкапа (выше).
4. После восстановления Mongo проверить `/health/ready` и то, что новые
   HTTP-запросы (не только health-check) реально проходят.

## Redis недоступен

Тоже сразу виден в `/health/ready` (`redis: "down"`). В отличие от Mongo,
затрагивает только OTP-флоу — `OtpService` не оборачивает вызовы Redis в
try/catch, поэтому `request-otp`/`verify-otp` при недоступном Redis падают
с générик `500 INTERNAL_SERVER_ERROR` (глобальный `HttpExceptionFilter`),
без специфичного кода ошибки. Уже открытые сессии (access/refresh JWT) не
зависят от Redis и продолжают работать — просмотр профиля, поиск, лайки,
чат и загрузка фото не затронуты. WebSocket rate limiter для чата — в
памяти процесса, не в Redis, тоже не затронут (см. README).

Действия: как для MongoDB (контейнер жив? healthcheck?
`docker compose restart redis`). Восстановление бэкапом не применимо —
для Redis сейчас нет backup/restore процедуры: только OTP-коды и
rate-limit счётчики с TTL, потеря этих данных при перезапуске Redis не
требует восстановления, просто означает, что уже выданные, но не
использованные коды нужно запросить заново.

## SMS-провайдер недоступен

Сейчас в проде — `SandboxSmsProvider` (реальные SMS не отправляются, см.
README, «SMS-провайдер для OTP» — AUTH-01 в `ROADMAP.md` сознательно не
завершена). Настоящего внешнего провайдера, который может лежать, пока
нет — этот сценарий актуален только после подключения реального
провайдера.

Когда провайдер подключат: `RetryingSmsProvider` уже оборачивает любую
реализацию `SmsProvider` тремя попытками с задержкой между ними. Если все
три не удались, `OtpService.sendOtp` бросает `502 OTP_DELIVERY_FAILED` —
клиент получает специфичный код, а не generic 500, и это видно в логах
как `HttpException` со статусом 502, не как необработанное исключение.
Никакого фолбэка на второй провайдер нет: при продолжительном отказе
единственного провайдера OTP полностью недоступен до его восстановления
или до переключения на другую реализацию в `SMS_PROVIDER`-фабрике
(`OtpModule`) с последующим передеплоем.

## Как узнать, что что-то случилось (важный текущий пробел)

- Sentry (если настроен `sentry.dsn`) уведомляет о необработанных 5xx
  через свой собственный механизм — независимо от Prometheus/Alertmanager.
- Правила `InstanceDown` и `HighErrorRate` (`observability/alerts.yml`)
  реально считаются Prometheus и видны в его UI, но
  `observability/alertmanager.yml` — заглушка без настоящего receiver
  (Slack/email/webhook). **Сейчас эти алерты никуда не доставляются** —
  единственный способ их увидеть — открыть Alertmanager/Prometheus UI
  руками. Это открытый пробел, а не описанная процедура: до того, как в
  `alertmanager.yml` появится реальный receiver, обнаружение инцидента
  зависит либо от Sentry, либо от ручной проверки.

## Смоук-проверка после любого из шагов выше

```bash
cd smoke && k6 run smoke.js
```

Проходит OTP → профиль → поиск → лайк → мэтч → чат → загрузка фото на
реальном окружении (REL-03, `smoke/README.md`) — быстрый способ убедиться,
что деплой/rollback/восстановление не просто поднял процесс, а оставил
рабочий продукт.
